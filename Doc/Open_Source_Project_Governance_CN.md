# Pyleecan 开源项目治理规范

## 1. 目标与适用范围

自当前节点起，`pyleecan` 按开源项目方式进行管理。代码日常协作以阿里云 Codeup `origin` 为主仓库，公共开源对齐以 GitHub `upstream` 为参考上游。

本规范覆盖以下五类管理要求：

1. 文档管理
2. 代码管理
3. 接口管理
4. 模块管理
5. Git 提交与 PR 管理

除紧急仓库修复外，不再接受直接在 `master` 上持续开发。

## 2. 角色定义

- `Maintainer`：负责方向、合并、发布、分支保护和治理裁决
- `Reviewer`：负责技术审查、接口兼容性审查、测试充分性审查
- `Contributor`：负责在特性分支提交代码、文档、测试和迁移说明

所有角色都必须遵守同一套分支、测试、文档和 PR 规则。

## 3. 文档管理规范

### 3.1 文档分层

- `README.md`：项目入口、安装方式、核心能力、贡献入口
- `CONTRIBUTING.md`：贡献流程、分支策略、提交流程、校验要求
- `CHANGELOG.md`：面向用户的版本变化记录
- `Doc/`：架构、接口、模块、验证、迁移、治理、ADR 等深入文档

### 3.2 文档更新触发条件

以下场景必须同步更新文档：

- 用户安装、运行、验证流程变化
- 模块职责变化
- 公共接口变化
- 外部依赖策略变化
- 贡献流程、分支流程、发布流程变化
- GUI 操作路径或输出结果变化

### 3.3 文档质量要求

- 文档必须描述当前真实行为，不允许保留失效说明
- 行为变更必须和代码在同一分支中完成
- 破坏性变更必须附带迁移说明
- 架构性决策必须记录到 `Doc/ADR/`

## 4. 代码管理规范

### 4.1 目录边界

- `pyleecan/Classes/`：数据模型、生成对象、受控属性入口
- `pyleecan/Methods/`：领域行为和算法实现
- `pyleecan/Functions/`：通用函数与跨模块辅助能力
- `pyleecan/GUI/`：PySide6 桌面界面
- `pyleecan/Generator/`：生成器、元数据、模式描述
- `Tests/`：与源码目录相对应的测试和回归
- `Doc/`：非执行性设计与说明

### 4.2 编码要求

- 默认遵循 Black 风格和 4 空格缩进
- 新逻辑必须落在正确模块层，不得将业务逻辑塞入测试、脚本或文档示例
- 引入可选依赖时，默认采用延迟导入，避免无关场景导入失败
- 行为修改必须附带定向测试
- 不得将本地构建产物、打包产物和临时验证结果纳入提交

### 4.3 变更粒度要求

- 一个分支聚焦一个主题
- 一个 commit 聚焦一个原子变化
- 代码修复、架构重构、文档重写、自动化改造不要混在一个 commit 里

## 5. 接口管理规范

### 5.1 受控接口范围

以下内容视为受控接口：

- `pyleecan` 对外公开的 Python API
- 机器、材料、仿真、配置等序列化数据结构
- GUI 中已对用户形成依赖的操作入口和导出流程
- 与 FEMM、GMSH、Elmer 等外部求解器的输入输出契约
- 测试、验证脚本中已经作为基线使用的输出形状、字段和路径约定

### 5.2 兼容性原则

- 默认要求向后兼容
- 如果必须破坏兼容，必须先出 ADR，再出迁移说明，再进 PR
- 能废弃不直接删除时，先走废弃周期
- 任何输出维度、字段名、配置项、文件格式变化，都必须补回归测试

### 5.3 接口变更分级

- `Patch`：修复缺陷，不改变既有调用方式
- `Minor`：兼容式扩展，新增字段、能力或参数
- `Major`：破坏兼容，需要迁移说明和版本计划

## 6. 模块管理规范

### 6.1 模块职责

每个模块必须清晰说明：

- 模块目的
- 上下游依赖
- 输入输出边界
- 对外暴露能力
- 测试入口

### 6.2 模块演进规则

- 新增模块前，先确认是否能复用现有目录和抽象
- 大型模块拆分、跨层依赖调整、核心依赖替换必须写 ADR
- 禁止形成 `Classes -> GUI -> Methods` 这类反向耦合链
- 模块移动或重命名时，必须同步更新导入、测试、文档和迁移说明

### 6.3 推荐的模块审查维度

- 是否职责单一
- 是否存在循环依赖
- 是否暴露了不应公开的内部细节
- 是否具备最小必要测试
- 是否对现有序列化或求解器契约造成影响

## 7. Git 与 PR 管理规范

### 7.1 分支策略

默认保护分支为 `master`。所有开发从 `master` 最新节点切出：

- `feature/<scope>-<short-description>`
- `fix/<scope>-<short-description>`
- `docs/<scope>-<short-description>`
- `refactor/<scope>-<short-description>`
- `release/<version>`

禁止长期在本地 `master` 上直接开发后再一次性提交。

### 7.2 提交规范

commit message 采用简短祈使句，推荐前缀：

- `[BF]` 缺陷修复
- `[FEAT]` 新功能
- `[DOC]` 文档
- `[REF]` 重构
- `[TEST]` 测试
- `[CI]` 流水线或自动化
- `[API]` 接口变更
- `[MOD]` 模块或架构调整
- `[REL]` 发布准备

### 7.3 PR 规范

PR 必须包含：

- 问题背景
- 解决方案摘要
- 影响范围
- 涉及模块
- 是否涉及接口兼容性变化
- 运行过的验证命令
- 若为 GUI 变更则附截图

PR 合并前必须满足：

- 至少一名 reviewer 审查
- CI 通过
- 评论线程已处理
- 文档、测试、迁移说明已补齐

### 7.4 合并策略

- 日常特性分支默认使用 `squash merge`
- 发布分支按发布流程单独处理
- 禁止在共享主分支上强推
- 特性分支在 review 前可自行整理 commit，但提交 review 后不应频繁重写历史

## 8. 必须在远端仓库开启的保护项

阿里云 Codeup 侧需要尽快开启以下配置：

1. `master` 保护，禁止直接 push
2. 合并必须走 PR
3. 必须通过质量门禁
4. 至少一名 reviewer 审批
5. 已解决 review 评论后方可合并

这些配置是流程的一部分，不是可选项。

管理员可按 [Doc/Codeup_Admin_Checklist_CN.md](Codeup_Admin_Checklist_CN.md) 中的落地清单逐项配置后台规则。

## 9. ADR 决策记录要求

以下情况必须新增 ADR：

- 公共接口破坏性变更
- 模块边界重构
- 外部核心依赖替换或版本策略调整
- 序列化格式升级
- 求解器集成方式的重大变化

ADR 模板见 [Doc/ADR/0000-template.md](ADR/0000-template.md)。

## 10. 当前节点后的执行要求

从本规范生效开始：

1. 所有新工作先切 `feature` 或其他 topic branch
2. 所有改动必须经过 PR
3. 所有功能改动必须同时考虑文档、测试、接口影响和模块边界
4. 所有对外可见变化都必须进入 `CHANGELOG.md`

本文件作为当前仓库治理基线，自当前分支起生效。
